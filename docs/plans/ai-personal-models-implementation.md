# Controlled personal models — implementation evidence

Personal registration now depends on an explicit, revisioned administrator grant to a subject or configured team. Registration, editing, selecting a helper and resolving a saved helper for generation all recheck current identity and capability. Revocation preserves registrations and permits owner deletion. Registration also requires the current editor/admin role; selection and generation reauthorize the current query role. Production destination checks reuse the shared-model HTTPS origin policy. The existing isolated development seam remains restricted to development login without an identity provider.

The policy has memory and PostgreSQL providers. PostgreSQL policy replacement uses compare-and-swap and appends the acting administrator and resulting grants in the same transaction. The default policy grants nobody. Connect methods expose the current capability, administrator-only grant lists, revisioned policy replacement, personal registration and owner deletion; existing REST/form registration passes through the same enforcement helper.

PostgreSQL personal credentials use the existing authenticated-encryption keyring. Ciphertext binds the personal namespace, subject, registration name, URL and model. A configured keyset enables an atomic startup migration: lock the legacy table, validate every existing encrypted row, encrypt legacy rows, blank their plaintext column and commit together. Missing keys leave a metadata/deletion-only store; they never enable a plaintext credential fallback. An invalid configured key or interrupted migration fails closed. The migration test exercises restart, wrong keys, missing keys, interruption rollback and metadata tampering, alongside persisted policy revisions and audit events.
