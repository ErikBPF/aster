# Versioned skills backend evidence

## Outcome and scope

The skill registry stores private skills, immutable numbered content revisions, and a separate current sharing policy. The owner controls content and sharing. A team publication requires current membership in a configured team; organization publication requires a current administrator. Recipients can read and use revisions but cannot edit the owner's skill. Historical revisions inherit the current audience, so retaining a revision identifier does not preserve access after sharing or membership is revoked.

The core `SkillStore` port has memory and PostgreSQL implementations. PostgreSQL stores immutable content rows separately from the current owner, latest revision, and sharing revision. Both content updates and sharing changes compare the supplied expected revision. The PostgreSQL adapter performs each mutation in a transaction and locks the skill header for content edits. No delete or executable-code workflow is exposed.

## Interface and bounds

`ListSkills`, `GetSkill`, `ListSkillVersions`, `PutSkill`, and `ShareSkill` use typed Connect RPC messages. New identifiers are opaque and generated by the server. The owner and author come from the authenticated principal. Listing and revision-history responses omit instructions and reference bodies; an authorized `GetSkill` fetches the requested content revision.

A skill contains a nonempty title (at most 160 bytes), nonempty instructions, and up to 16 named text references. Reference names are at most 128 ASCII bytes and contain only letters, digits, periods, underscores, or hyphens; `.` and `..` are rejected. Duplicate names and NUL content are rejected. The aggregate title, instructions, names, and reference bodies may not exceed 32 KiB. Text is stored as data; the registry neither executes it nor resolves file paths or URLs.

Shared listing resolves fresh identity once per request. Team reads recheck current membership; authority failure hides shared results and denies individual shared reads. Private owner access does not depend on the shared identity provider. The isolated development identity seam remains explicit.

## Evidence and remaining validation

Apollo core tests first compiled against a nonfunctional registration seam and produced two assertion failures on registration. After implementing the memory store, all three core tests passed (`/tmp/aster-skills-core-red.log`, `/tmp/aster-skills-core-green.log`). RPC tests subsequently failed with HTTP 501 versus expected 200 against compiling RPC seams (`/tmp/aster-skills-api-red.log`). Earlier compilation failures in that receipt are infrastructure/type-integration repairs, not RED evidence.

Final RPC/current-authority validation passed on Apollo: all three integration tests passed (`/tmp/aster-skills-final-green.log`). They cover private isolation, owner edits, immutable content, stale writes, administrator publication, current sharing revocation, team membership removal, authority outage, and exactly one authority lookup for a two-skill shared listing. Independent review also exposed a stale-role team-publication gap: the regression first failed with HTTP 200 versus expected 403 (`/tmp/aster-skills-current-role-red.log`); authorizing the refreshed principal for writing closed it. Disposable PostgreSQL validation is recorded in the main implementation report. The isolated PostgreSQL recipe verifies persistence after adapter reconstruction, immutable historical content, current sharing on historical reads, and conflict rejection. These tests do not prove browser behavior or deployed behavior; those remain separate gates owned by the integration workflow.
